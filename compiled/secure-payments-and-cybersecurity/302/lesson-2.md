# Point-to-Point Encryption (P2PE)

TLS protects data between your server and the gateway. Point-to-point encryption (P2PE) protects data from the moment a card is read on the terminal to the moment the gateway decrypts it. P2PE closes the gap that TLS does not cover: the path from the physical card to your application server.

## How P2PE works

In a P2PE-enabled terminal, card data is encrypted inside the terminal hardware the instant the card is read — before the data touches the terminal's software or your application. The encryption key is managed by the payment processor, not by the merchant.

The encrypted data travels from the terminal through your application server to the gateway. Your application server passes it through without being able to read it. Only the gateway, which holds the decryption key, can recover the original card data.

## Why this matters for your integration

Without P2PE, your application server receives readable card data (or a card token generated by software running on the terminal). With P2PE, your application server receives encrypted data it cannot decrypt.

The practical consequence: a breach of your application server in a P2PE environment exposes no card data. There is nothing there to steal.

## What P2PE removes from your scope

Payment compliance (PCI DSS, covered in Module 304) requires extensive controls for any system that touches card data. P2PE removes your application server from that scope because your server never has access to readable card data.

This significantly reduces the compliance burden and the risk profile of your integration.

## What P2PE does not protect

P2PE protects card data from the read point to the gateway. It does not protect:

- Data after the gateway decrypts it (the gateway's responsibility)
- Transaction metadata stored in your database (amounts, timestamps, merchant IDs)
- Credentials used to call the gateway API

These require separate controls, which this course covers in the remaining modules.
